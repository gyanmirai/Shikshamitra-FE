## 0. Decisions already made

These were reviewed and locked in before this plan was written — do not re-litigate them without a new discussion:

1. **Collection Policy owns late fee + waiver rules directly.** The separate, unrouted `ILateFeePolicy` type/drawer/hook (`LateFeePolicyDrawer.tsx`, `useLateFeePolicyForm.ts`, `LateFeePolicyWorkspace.tsx`) is **retired**, not kept as a parallel system. There is exactly one place a school configures late fee behaviour.
2. **Backend adopts the full HR Policies pattern from day one**: aggregate root + version history + assignment/impact-analysis tracking, modeled on `src/ShikshaMitra.Domain/HR/Policies/Aggregates/*` (`AttendancePolicy`, `PayrollPolicy`, `HrPolicyVersion`, `HrPolicyAssignment`). No "simple CRUD now, version later" shortcut.

### 0.1 Decisions carried in from the ecosystem-gaps review

These resolve the open ownership questions raised in `collection-policy-ecosystem-gaps.md`. They are this plan's recommended defaults — confirm with stakeholders before Phase 0 executes, since Phase 0 now has a hard dependency on decision 3 (below), but do not treat them as any less binding than §0 above once confirmed; they are written into every phase that follows.

3. **`IPaymentPolicy` is canonical for payment-behaviour fields; `IPaymentTerm` is narrowed to installment-schedule shape only.** `IPaymentTerm`/`IInstallment` (`PaymentTerm/type.ts`) keeps `installments[]` (dates, sequence, demand/reminder toggles per installment) and `holidayShiftingMethod` (due-date shifting is a scheduling concern, not a payment-behaviour one). It loses `allowAdvancePayment`, `minAdvanceDays`, `maxAdvanceMonths`, `allowFullYearPayment`, `allowPartialInstallment`, `minPartialAmount`, `minPartialPercentage`, and the top-level reminder fields — all of these are governed by the `IPaymentPolicy` attached to the same Fee Structure instead. `IInstallment.allowPartialOverride` is kept as the one legitimate per-installment escape hatch (see decision 3a below).
   - **3a. Per-installment override precedence**: when `IInstallment.allowPartialOverride` is explicitly set (true or false) on an installment, it wins for that installment; when left unset, the installment inherits `IPaymentPolicy.allowPartialPayment`. This is the only field allowed to override the policy per-installment — every other payment-behaviour field is policy-level only, to avoid recreating a second per-field override surface.
4. **`IInstallment.lateFeePolicyId` is re-pointed at Collection Policy (via the Fee Structure attachment), not carried into the post-`ILateFeePolicy` world as a dangling reference.** Concretely: the field is removed from `IInstallment` — grace period and late fee are resolved solely through the Fee Structure's `collectionPolicyId` (Phase 1's resolution algorithm, §0.1 decision 6), with `IInstallment.gracePeriod` kept only as an optional per-installment override of Collection Policy's `gracePeriodDays`, following the same override-if-set/inherit-if-null pattern as decision 3a.
5. **The Phase 1 backend aggregate is designed as a shared, generalized framework** (`FinancePolicyAggregateBase`, `FinancePolicyVersion`, `FinancePolicyAssignment`) even though only `CollectionPolicy` is fully implemented in Phase 1. Payment/Concession/Refund/Proration policies attach to the same base classes when their own backend phases happen (Payment Policy's is Phase 6 of this plan), instead of each re-deriving the aggregate/versioning/assignment-tracking pattern from scratch.
6. **Student Override is scoped to a small flag set (`StudentFeePolicyOverride`), not a full per-student policy clone.** `isLateFeeExempt`, `customGracePeriodDays`, `waiverPreApproved` + reason — layered on top of the resolved Fee Structure/School-Default policy, never a standalone policy object. If a school need surfaces that genuinely requires more, that's a new discussion, not an assumed extension of this plan.

## 2. Guiding principles for this build

- **Single source of truth for calculation.** The late-fee/waiver math must live in exactly one service, called by both the backend Fee Collection engine and the frontend preview/calculator (via API), so they can never drift.
- **Enforcement over configuration.** Every field in the policy editor must have a corresponding runtime consumer. A field nobody reads is worse than no field — it's a promise the system doesn't keep.
- **Money changes are auditable and reversible in intent.** Waivers, adjustments, and policy version changes must all be attributable (who/when/why) and must not silently rewrite what a family already owed.
- **No new duplication.** Where Concession, Adjustment, or Refund policies already own a concept (e.g. `lateFeeBehaviour`), Collection Policy must defer to them with an explicit, documented precedence rule rather than re-implementing.

### Phase 1 — Backend: aggregate & versioning foundation

**Goal:** give Collection Policy a real, persistent, versioned home in the backend, following the HR Policies pattern — and lay the shared groundwork (§0.1 decision 5) that Payment Policy's own backend (Phase 6) plugs into later instead of re-deriving it.

- **Domain layer, shared base** (`ShikshaMitra.Domain/Finance/Policies/Aggregates/Shared/`) — new in this revision of the plan, per §0.1 decision 5:
  - `FinancePolicyAggregateBase` — abstract base carrying the fields every `IFinancePolicyBase`-shaped kind needs: `policyName`, `policyCode`, `status`, `academicYearId`, `effectiveFrom/To`, `isDefault`, `description`, plus a `policyType` discriminator column. `CollectionPolicy` (below) is the first concrete subclass; `PaymentPolicy` (Phase 6) is the second.
  - `FinancePolicyVersionBase` / `FinancePolicyAssignmentBase` — the version-snapshot and assignment-tracking shape generalized from `HrPolicyVersion`/`HrPolicyAssignment`, so `CollectionPolicyVersion`/`CollectionPolicyAssignment` (below) and Phase 6's `PaymentPolicyVersion`/`PaymentPolicyAssignment` share one persistence and impact-analysis code path rather than two copies.
  - **Server-side enforcement of the "one `isDefault` per `academicYearId` per `policyType`" invariant** (Phase 0's client-side check made authoritative) — reject on save with a clear, field-level error rather than silently allowing two defaults to coexist.
- **Domain layer** (`ShikshaMitra.Domain/Finance/Policies/Aggregates/CollectionPolicy/`):
  - `CollectionPolicy` aggregate root, extending `FinancePolicyAggregateBase`.
  - `LateFeeRule` value object — `enableLateFee`, `gracePeriodDays`, `lateFeeApplyOnFeeHeads`, `lateFeeType`, `flatAmount`, `percentage`, `percentageBase`, `amountPerDay/Week/Month`, `compoundFrequency`, `roundingMethod`, `considerAsIncome`, `lateFeeIncomeHeadId`, a **`maximumLateFeeAmount`** cap field (closes the "runaway compounding" gap identified in the review doc), and two new fields from `Collection_Policy_Design_Recommendations.md` §2: **`maximumChargingDays`** (nullable — stop accruing late fee after N days overdue, independent of the amount cap) and **`gracePeriodType`** (`Calendar` / `WorkingDay` — grace period counted in calendar days or working days; working-day counting requires an academic-calendar/holiday-list lookup, confirm one exists — see Open Questions).
  - `EscalationRule` child entities (slabs) — `startDay`, `endDay`, `calculationType`, `value`, `maxFee`, with **server-side continuity/overlap validation** enforced on save (defense in depth beyond the Phase 0 client-side check).
  - `WaiverRule` value object — `enableWaiver`, `waiverApplyOnFeeHeads`, `maximumWaiverAmount`, `maximumWaiverPercentage`, `waiverExpiry`, plus **new** `requiresApproval` + `approvalRoleIds` + `approvalThresholdAmount` fields (closes the "no approval workflow" gap).
  - `OnlineCollectionSetting` — `allowOnlineCollection` (structure-level on/off gate; per-method economics live on `PaymentPolicy` in Phase 6/4i — see Phase 4i for the precedence rule between the two).
  - `CollectionPolicyVersion` : `FinancePolicyVersionBase` — immutable snapshot of the above on every publish-affecting edit; DueFee generation records which version ID applied.
  - `CollectionPolicyAssignment` : `FinancePolicyAssignmentBase` — tracks which Fee Structure cards / academic years reference this policy; powers "policy in use by N structures / M students" checks.
  - **`StudentFeePolicyOverride` entity** (per §0.1 decision 6) — `studentId`, `feeStructureId`, `isLateFeeExempt: bool`, `customGracePeriodDays: int?`, `waiverPreApproved: bool`, `waiverPreApprovalReason: string?`, `createdByUserId`, `createdAt`. Not versioned like the policy itself (it's a student-specific adjustment, not a rule change) but every create/update is audit-logged the same way a waiver is (Phase 3's audit mechanism).
  - **`resolveCollectionPolicy(feeStructureId, academicYearId)` domain service method** — the single resolution algorithm every consumer (collect form, parent portal, `/simulate`, impact preview) must call: (1) Fee Structure's direct `collectionPolicyId` attachment → (2) the academic year's `isDefault` Collection Policy → (3) `null` (no policy attached — matches `collection-policy-flow.md` §7.10's existing "No Collection Policy Attached" scenario: no late fee, no waiver, online collection allowed by default). A second method, `resolveEffectiveRulesForStudent(studentId, feeStructureId)`, layers `StudentFeePolicyOverride` flags on top of whatever `resolveCollectionPolicy` returns — override composition happens in exactly one place, not once per caller.
- **Application layer**: DTOs mirroring `ICollectionPolicy` plus the new cap/approval/`maximumChargingDays`/`gracePeriodType` fields; `CollectionPolicyAppService` (create, update — creates new version, archive/restore, clone, list versions, impact-preview); `StudentFeePolicyOverrideAppService` (create/update/list-by-student, get-effective-rules).
- **HttpApi layer**: `CollectionPoliciesController` (`GET/POST/PUT/PATCH/DELETE /api/finance/collection-policies`, `GET .../{id}/versions`, `GET .../{id}/impact`), replacing the generic `/finance-policies` stub for this policy type specifically. (Other policy kinds keep using the generic slice until their own backend phase — Payment Policy's is Phase 6.) New: `PUT /api/finance/students/{studentId}/fee-structures/{feeStructureId}/policy-override`, `GET .../policy-override` (returns the override plus the resolved effective rules, for the frontend override-editing UI below).
- Wire the existing but unused `Finance.Policies.CollectionPolicy.{View,Add,Delete}` permissions into the controller; add `Edit`/`Archive`/`ApproveWaiver` permissions following the same constants file pattern; add `Finance.Policies.CollectionPolicy.EditStudentOverride` for the new override endpoints (a student-level exemption is a more sensitive action than a normal edit and should not automatically inherit the same permission).
- EF Core entity configuration + migration (covers `FinancePolicyAggregateBase`/`FinancePolicyVersionBase`/`FinancePolicyAssignmentBase` as a shared table-per-hierarchy or table-per-type strategy — pick one consistent with how `HrPolicy*` is already mapped — plus `CollectionPolicy`'s own tables and the new `StudentFeePolicyOverride` table).
- **Frontend**: point `financePolicy.ts` (or a new dedicated `collectionPolicy.ts` slice, mirroring the backend split) at the real endpoints, replacing `body: any` with typed request DTOs matching the backend contract. New: a **Student Fee Policy Overrides** section — a small, explicit UI (e.g. a card in the student's fee profile screen, not buried in Collection Policy's own drawer, since it's set per-student not per-policy) with the three flag toggles (`isLateFeeExempt`, `customGracePeriodDays`, `waiverPreApproved`) and a mandatory reason field for `waiverPreApproved`, calling the new override endpoints and displaying the resolved effective rules read-only alongside the raw override flags so staff can see the combined result, not just what they just typed.

**Exit criteria:** Creating/editing/archiving a Collection Policy through the existing UI actually persists to a database, with version history visible in the existing (currently-decorative) Version History drawer; `resolveCollectionPolicy`/`resolveEffectiveRulesForStudent` are the only code paths that determine "which policy and which effective rules apply here," verified by grepping for any other place a `collectionPolicyId` is looked up ad hoc; a student marked `isLateFeeExempt` shows zero late fee on `/simulate` regardless of the attached policy's configuration.

### Phase 2 — Backend: shared calculation service

**Goal:** one authoritative implementation of the late-fee/waiver math, per the algorithm already documented in `collection-policy-flow.md` §5.

- `LateFeeCalculationService` (Domain service) implementing, **in this fixed order** (each step can short-circuit the ones after it, so the order is load-bearing, not just a checklist):
  1. Call `resolveEffectiveRulesForStudent` (Phase 1) to get the resolved `CollectionPolicy` plus any `StudentFeePolicyOverride` — if `isLateFeeExempt`, return zero immediately, skip everything below.
  2. Check for an active `CollectionPolicyExceptionWindow` (Phase 4j) covering the due date's overdue period for the relevant scope — `SuspendLateFeeAccrual` returns zero for the days inside the window (days outside it still accrue normally); `ExtendGracePeriod` adds the window's extra days to the effective grace period for step 3.
  3. Grace-period offset — using `customGracePeriodDays` (student override) if set, else the policy's `gracePeriodDays`, adjusted for `gracePeriodType` (`Calendar` vs `WorkingDay`, Phase 1) and any exception-window extension from step 2.
  4. Per-fee-head override resolution (Phase 4a) — `NoLateFee` short-circuits to zero for that fee head; `CustomRule` swaps in the fee-head-level `LateFeeRule` for the remaining steps; `Inherit` proceeds with the policy-level rule.
  5. The 7 calculation types (Flat, Percentage, PerDay, PerWeek, PerMonth, Compound, Slab) exactly as before.
  6. Apply `maximumLateFeeAmount` cap and `maximumChargingDays` cutoff (Phase 1's new fields) — whichever binds first wins.
  7. Apply rounding method.
- `WaiverCalculationService` — effective waiver = `min(requested, maxWaiverAmount, lateFee × maxWaiverPercentage / 100)`, with expiry check; if `StudentFeePolicyOverride.waiverPreApproved` is set, the standard approval-workflow step (Phase 3) is skipped but the cap/expiry checks still apply — pre-approval waives the approval step, not the ceiling.
- Unit tests covering the 15 scenarios already catalogued in `collection-policy-flow.md` §7 (compound + partial payment, slab overlap/gap, waiver cap exceeded, concession conflict, grace period = 0, archived-policy handling, etc.) as concrete test cases, not just prose — **plus** new scenarios for each step above: student exempted mid-cycle, exception window covering only part of an overdue period, working-day grace period crossing a holiday, `maximumChargingDays` cutoff reached mid-slab.
- Expose a **preview endpoint** (`POST /collection-policies/{id}/simulate`) taking an outstanding amount + days-late (or a real student ID) and returning the computed late fee **plus which of steps 1–7 above applied and why** (e.g. `"exempt": false, "exceptionWindowApplied": "GatewayOutage-2026-08", "cappedBy": "maximumLateFeeAmount"`) — this becomes the backing for both an improved Live Calculator (Phase 5) and a "preview against currently overdue students before publishing" tool, and the explanation string shown to cashiers/parents in Phase 3.

**Exit criteria:** Late fee math is computed identically whether triggered from a real collection, an impact preview, or the calculator — because it's the same code path — and the `/simulate` response's step-by-step explanation is always sufficient on its own to answer "why was this amount charged/not charged," without needing to read the policy configuration separately.

### Phase 3 — Fee Collection runtime integration (highest priority for actual usefulness)

**Goal:** make the policy real at the point of collection. This is the phase that turns Collection Policy from "a form that saves JSON" into an actual control.

- `GET /fee-collections/{studentId}/collect-form` extended to resolve the student's fee structure → `collectionPolicyId` → active version, and return computed late fee per due line using the Phase 2 service.
- `FeeCollectionForm.tsx`: add a late-fee column/breakdown per due line, with a one-line explanation of how it was calculated (closes the "parent/cashier transparency" gap).
- Waiver action in the collect flow: amount/percentage input, enforced against `maximumWaiverAmount`/`Percentage`/`waiverExpiry`, mandatory reason field, and an approval step when `requiresApproval` / above `approvalThresholdAmount` is configured (ties into Phase 1's new `WaiverRule` fields).
- Every waiver application recorded as an auditable event (who/when/why/amount), surfaced in the existing Audit Trail drawer.
- Payment method list in the collect form filtered by `allowOnlineCollection` — extend to also gate the parent portal's online payment option, not just the staff-facing collect form.
- **Concession precedence**: implement and document the rule that `IConcessionPolicy.lateFeeBehaviour` (`Recalculate` / `KeepExisting` / `RemoveLateFee`) always takes precedence over Collection Policy's own late-fee output on concession-applied heads.
- **Adjustment precedence**: `AdjustmentForm.tsx` / its backend counterpart consults the resolved Collection Policy's waiver caps before allowing a manual reduction that behaves like a waiver.
- Clarify and implement charges-vs-fee-heads applicability: add `applyToCharges` flag to `LateFeeRule` (closes doc gap #6) and honor it in the calculation service.
- **Precedence surfaced in plain language**: the Concession/Adjustment precedence rule above must be visible to admins, not just enforced silently in code. Add a small info banner (e.g. `PolicyPrecedenceNote.tsx`) to (a) the Collection Policy summary sidebar when a fee head it applies to also has an active Concession policy attached, and (b) the Fee Structure attachment step where Collection Policy is linked. Wording pattern: *"Concession overrides late fee on the fee heads it applies to."* Sourced from a single constants file (not duplicated inline strings) so the rule text and the enforcement logic can't drift apart. (Closes gaps doc §4.2, bullet 2.)

#### 4h. Fee Clearance Gate (closes ecosystem-gaps doc §3)

**Goal:** let schools block a certificate/service (hall ticket, report card, promotion, admission renewal, leaving certificate, ID card) when a student has outstanding dues, without making Collection Policy responsible for enforcing it inside modules it doesn't own.

- **Data model**: `FeeClearanceRule` — small aggregate, own `policyType: 'clearance'` (not a field on `CollectionPolicy` — see ecosystem-gaps doc §3 for why). Fields: `blockedActions: FeeClearanceAction[]` (`HallTicket | ReportCard | Promotion | AdmissionRenewal | LeavingCertificate | IDCard | Custom`), `outstandingThresholdAmount: decimal?` (block only above this; null = block on any outstanding), `gracePeriodDaysBeforeBlock: int` (don't block immediately on the due date), `overrideRoleIds: string[]` (roles allowed to force-issue despite a block).
- **API**: `GET /api/finance/students/{studentId}/fee-clearance-status` → `{ isCleared, blockedActions: FeeClearanceAction[], outstandingAmount, reasonDetail }`. This is the **one** shared query surface — every consumer module calls this, none re-implements an outstanding-dues check. `POST /api/finance/students/{studentId}/fee-clearance-override` (`action`, `reason`, mandatory) for the authorized-role escape hatch, audit-logged the same way a waiver is.

- **Frontend**: `FeeClearanceRule` editor (new drawer under the Policies module, following the same 4-section-form conventions as Collection Policy); each consumer screen (e.g. `LeavingCertificate.tsx`, hall-ticket generation, promotion screen) adds a pre-action clearance check with a blocking dialog showing `reasonDetail` and, for authorized roles, an "Override with reason" button.
- **Acceptance criteria**: a student with outstanding dues above the configured threshold cannot generate a hall ticket through the normal flow and sees a clear reason; an authorized role can override with a mandatory reason that appears in the Audit Trail; a student below the threshold or within `gracePeriodDaysBeforeBlock` is unaffected.

#### 4i. Granular online-collection economics (closes ecosystem-gaps doc §4)

**Goal:** replace the single `allowOnlineCollection` boolean's blind spot — per-method control, convenience-fee economics, and time-of-day/holiday gating — without duplicating it into a second boolean set.

- **Data model**: extend `IPaymentPolicy.paymentModes` (Phase 6, once confirmed canonical per §0.1 decision 3) — per online method (`upi`, `card`, `neft`, `onlineGateway`), add `convenienceFeeType: 'None' | 'FlatAmount' | 'Percentage'`, `convenienceFeeValue: decimal?`, `convenienceFeeBornBy: 'School' | 'Parent'`, `minAmount: decimal?`, `maxAmount: decimal?`. School-level (not per-method) `onlineCollectionWindow`: `startTime`/`endTime` (working-hours-only gating), `disableOnHolidays: bool` (requires an academic-calendar/holiday lookup — confirm one exists, see Open Questions; if not, ship time-window gating first and hold the holiday flag behind a "coming soon" state rather than silently no-op it).
- **Precedence with Collection Policy's `allowOnlineCollection`**: both gates apply — Collection Policy's flag is the structure-level on/off switch; `PaymentPolicy.paymentModes[method]` and the window/holiday checks are the method-level and time-level filters on top. A payment method is offered only if **all** applicable gates allow it (most-restrictive-wins), evaluated at payment **initiation** (an in-flight payment that starts before a window closes is allowed to complete).
- **API**: extend the collect-form and parent-portal payment-method resolution to run all three checks (structure-level, method-level, window/holiday) and return only the allowed subset, each tagged with its resolved convenience fee (if any) for display.
- **Frontend**: `FeeCollectionForm.tsx` and the parent portal payment screen show the convenience fee **itemized separately** from the fee amount for any method where `convenienceFeeBornBy: 'Parent'` — never folded silently into the total — on both the payment screen and the receipt.
- **Acceptance criteria**: a school configuring UPI with a 2% convenience fee borne by the parent shows that fee as a separate line item in the collect form, the parent portal, and the receipt; a payment method disabled outside working hours disappears from the method list after the configured `endTime` but an already-started payment before that time completes normally.

#### 4j. Exception windows (closes ecosystem-gaps doc §5)

**Goal:** let a school suspend late-fee accrual proactively for a defined window (gateway outage, natural disaster, bank strike) instead of relying on Bulk Waiver (4d) to forgive fees that were already, incorrectly, charged.

- **Data model**: `CollectionPolicyExceptionWindow` — `scope` (`SchoolWide | AcademicYear | FeeStructure | ClassSection`), `scopeId: string?`, `startDate`, `endDate`, `effect` (`SuspendLateFeeAccrual | ExtendGracePeriod` with an `extensionDays` value when that effect is chosen, `| DisableOnlineCollection | Custom`), `reasonCode` + free-text `reason`, `createdByUserId`, `createdAt`. The window's own creation is audit-logged; individual due lines inside the window are **not** individually audit-logged the way Bulk Waiver entries are, since nothing was charged to reverse.
- **Calculation service integration**: Phase 2's `LateFeeCalculationService` step 2 (already specified above) checks for an active window covering the relevant scope and date range before running the grace/slab pipeline.
- **API**: `POST /api/finance/collection-policies/exception-windows` (create), `GET .../exception-windows?scope=&activeOn=` (list/check), `DELETE .../exception-windows/{id}` (only before `startDate`; once active, an admin creates a corrective window rather than deleting history).
- **Frontend**: an "Exception Windows" admin action (Collection Policy list toolbar or Finance admin menu) — scope picker, date range, effect picker, reason — visually and functionally distinct from the Bulk Waiver action (4d) so admins don't reach for the wrong tool: Bulk Waiver forgives what's already charged; Exception Window prevents charging in the first place.
- **Acceptance criteria**: creating a `SuspendLateFeeAccrual` window for a date range results in zero late fee computed (via `/simulate`) for any due date whose overdue period falls inside it, with no manual waiver action required; the window's creation is visible in Audit Trail.

**Exit criteria:** every capability listed in `collection-policy-review-and-gaps.md` §4 **and** every gap identified in `collection-policy-ecosystem-gaps.md` §3–§5 has a corresponding implemented feature, verifiable against the acceptance criteria above — not just fields that happened to already be in the original form.

It reuses the shared framework from Phase 1 (§0.1 decision 5) rather than rebuilding it.

- **Domain layer** (`ShikshaMitra.Domain/Finance/Policies/Aggregates/PaymentPolicy/`):
  - `PaymentPolicy` aggregate root, extending `FinancePolicyAggregateBase` (Phase 1).
  - Fields per the confirmed-canonical `IPaymentPolicy` shape (§0.1 decision 3): `allowPartialPayment`, `minimumPaymentType`, `minimumPaymentValue`, `allocationMethod` (`FeeHeadPriority | Proportional | FIFO | Manual`), `advancePaymentAllowed`, `advancePaymentMaxAmount`, `advancePaymentCarryForward`, `receiptGeneration`, `autoDemand`, `autoReminder` + reminder fields, `paymentModes` (extended with the convenience-fee/window fields from Phase 4i), `requireApprovalAboveAmount` + `approvalRoleIds`, `allowRefund`/`allowAdjustment`/`allowWriteOff`.
  - `PaymentPolicyVersion` : `FinancePolicyVersionBase`, `PaymentPolicyAssignment` : `FinancePolicyAssignmentBase` — same pattern as Collection Policy.
  - `PaymentAllocationService` (Domain service) — **formalizes the currently-hardcoded `allocatePayment()` logic** referenced in `collection-policy-flow.md` §3.1 into a policy-driven service: given a payment amount and a set of due lines, allocates according to the resolved `PaymentPolicy.allocationMethod` (`FIFO` = oldest due first, `FeeHeadPriority` = configured fee-head order, `Proportional` = split pro-rata across all outstanding, `Manual` = caller-specified allocation, validated against the policy's `allowPartialPayment`/`minimumPaymentValue` constraints). This replaces the hardcoded allocation logic, not sits alongside it.
- **Application/HttpApi layers**: `PaymentPolicyAppService` + `PaymentPoliciesController` (`GET/POST/PUT/PATCH/DELETE /api/finance/payment-policies`, `.../{id}/versions`, `.../{id}/impact`), mirroring Phase 1's `CollectionPoliciesController` structure exactly.
- **Fee Collection runtime integration** (mirrors Phase 3, for Payment Policy instead of Collection Policy):
  - `GET /fee-collections/{studentId}/collect-form` resolves the student's `PaymentPolicy` the same way it resolves `CollectionPolicy`, and returns `allowPartialPayment`/`minimumPaymentValue`/`allocationMethod`/allowed `paymentModes` alongside the existing late-fee data.
  - `FeeCollectionForm.tsx`: enforce `minimumPaymentValue`/`minimumPaymentType` on partial payment entry (currently unvalidated against any policy); filter the payment-method selector by the resolved `paymentModes` (structure-level `allowOnlineCollection` from Collection Policy **and** method-level `paymentModes` from Payment Policy both apply — see Phase 4i's precedence rule); enforce `advancePaymentMaxAmount` when a payment exceeds current dues; require approval when `requireApprovalAboveAmount` is configured, same UI pattern as the Phase 3 waiver-approval step.
  - Parent portal payment screen: same constraints, same resolution path — no separate parent-side validation logic, per the Phase 3 parity principle.
- **`PaymentTerm` integration**: once narrowed to installment-schedule-only (Phase 0), each `IInstallment.allowPartialOverride` (when explicitly set) overrides the resolved `PaymentPolicy.allowPartialPayment` for that installment only (§0.1 decision 3a) — implemented as one more input to `PaymentAllocationService`, not a separate check.
- **Frontend**: wire `PaymentPolicyDrawer.tsx`'s currently no-op `onSubmit` (`PaymentPolicyDrawer.tsx:952`) to the new endpoints via a dedicated `paymentPolicy.ts` redux slice (replacing the generic `financePolicy.ts` `/finance-policies` calls for this policy type, matching Phase 1's split for Collection Policy).
- **Acceptance criteria**: a Payment Policy configured with `allocationMethod: FIFO`, `minimumPaymentValue: ₹500`, and only `cash`+`upi` enabled results in: a payment attempt below ₹500 being rejected in the collect form with a clear message; a payment automatically allocated oldest-due-first; and card/NEFT disappearing from the payment method list — all verified in a real collect-form run, not just the policy editor.

**Exit criteria:** `IPaymentPolicy` reaches the same state Collection Policy reaches at the end of Phase 3 — persisted, versioned, and actually enforced at the point of collection on both the staff and parent-facing surfaces — closing ecosystem-gaps doc §1's core finding that Payment Policy was equally unbuilt.

## 4. Sequencing & dependencies

```
Phase 0 (FE cleanup + Payment/Term de-dup)  ──────────────┐
                                                            │
Phase 1 (BE aggregate/versioning/resolver/overrides) ──────┼──► Phase 3 (Fee Collection integration) ──► Phase 4 (school-workflow features: 4a–4j)
                                                            │                    │                                        │
Phase 2 (BE calc service, exception/override-aware) ───────┘                    │                                        │
                                                                                 ▼                                        ▼
                                                                          Phase 6 (Payment Policy BE + runtime,   Phase 5 (polish/docs)
                                                                          reuses Phase 1's shared framework)
```

- Phase 0 has no backend dependency and can start immediately, but now has an internal ordering constraint: the `IPaymentPolicy`/`IPaymentTerm` de-duplication and `lateFeePolicyId` re-pointing must land before or alongside the `ILateFeePolicy` deletion (§0.1 decisions 3/4).
- Phases 1 and 2 can proceed in parallel with each other and with Phase 0. Phase 1's shared `FinancePolicyAggregateBase`/`Version`/`Assignment` framework should be designed (not necessarily fully implemented beyond Collection Policy) before Phase 6 starts, so Phase 6 doesn't have to retrofit onto a Collection-Policy-only shape.
- Phase 3 depends on both Phase 1 (persisted, resolvable policy + assignments + `StudentFeePolicyOverride`) and Phase 2 (calculation service, including the exception-window/override-aware ordering) being done.
- Within Phase 4: **4a** (per-fee-head overrides) depends on Phase 3's calculation integration and should go first, since 4d (bulk waiver) and 4g (reporting) both read per-fee-head-resolved data. **4e** (role-scoped permissions) has no hard dependency on the others and can be done any time after Phase 1. **4c** (notifications) is blocked on resolving open question 1 below and can slip without blocking the rest. **4f** (multi-year continuity) only needs Phase 1's assignment tracking. **4g** (reporting) depends on 4d for the bulk-waiver audit source and on Phase 3 for the individual-waiver audit source. **4h** (Fee Clearance Gate) depends on Phase 3's outstanding-dues computation but is otherwise independent — its main risk is cross-team coordination with Certificates/Academic/Admission/Examination modules, not internal sequencing. **4i** (online-collection economics) depends on Phase 6 existing far enough to have a `PaymentPolicy.paymentModes` to extend — schedule 4i after Phase 6 starts, not in parallel with early Phase 4. **4j** (exception windows) depends on Phase 2's calculation-service hook point (step 2 in the fixed order) and should land before or alongside 4d, since it changes when admins reach for Bulk Waiver vs. an Exception Window.
- Phase 5 can start once Phase 2 (for the calculator) and Phase 1 (for assignment-based warnings) are available; documentation sync can happen any time but is cleanest as a final step.
- Phase 6 depends on Phase 0 (decision 3 executed — `IPaymentPolicy` confirmed canonical) and Phase 1 (shared framework available). It can otherwise proceed in parallel with Phase 3/4, since it touches a different policy kind — the only shared surface is `FeeCollectionForm.tsx` and the parent portal, which both phases modify, so coordinate those specific file changes to avoid merge conflicts rather than sequencing the whole phases against each other.

## 5. Open questions to resolve before/during Phase 1

These weren't blocking enough to hold up this plan, but should be confirmed with stakeholders before the corresponding phase starts:

1. Does the platform have an existing notification/reminder infrastructure Phase 4's notification hooks should plug into, or does one need to be built?
2. Is per-school feature-flagging available for staging the Phase 3 rollout, or will it ship to all schools simultaneously?
3. Should `maximumLateFeeAmount` (new cap field, Phase 1) be mandatory or optional — i.e., should the system refuse to publish an uncapped Compound/Percentage policy, or just warn? (Determines the severity of Phase 4b's validation warning.)
4. For multi-structure students (doc's §7.13 edge case — a student with fee heads from multiple fee structures, each with a possibly different Collection Policy), does late fee calculation need to happen strictly per-structure, or is an aggregate view ever required for reporting?
5. What is the intended default role-to-permission mapping for waiver approval (Phase 4e) — e.g. does "Accountant" map to `ApproveWaiver` only and "Principal" to `ApproveWaiverAboveThreshold`, or does each school configure this independently? Needed before 4e's permission seeding can be finalized.
6. Does a per-fee-head override (Phase 4a) need its own independent waiver cap/expiry, or does it always inherit the policy-level `WaiverRule`? The plan above assumes overrides only affect late-fee calculation, not waiver terms — confirm before implementing 4a if waiver-per-head is also required.
7. Is there an existing academic-calendar/holiday-list service to back `gracePeriodType: WorkingDay` (Phase 1) and `disableOnHolidays` (Phase 4i)? If not, both features need to either be deferred or paired with a minimal holiday-list feature of their own — confirm before Phase 1 implements `WorkingDay` grace-period counting.
8. Confirm §0.1 decision 3 (`IPaymentPolicy` canonical, `IPaymentTerm` narrowed) with whoever owns the `PaymentTerm` module before Phase 0 executes — it's this plan's recommended default, not yet a discussion that happened with that module's stakeholders.
9. Which team/module owns the Certificates, Promotion, Admission Renewal, and Examination (hall ticket) screens that Phase 4h's Fee Clearance Gate needs to integrate with? Needed to schedule 4h's cross-module consumer work realistically — it's the one Phase 4 item that isn't entirely within the Finance module's own codebase.
10. Confirm §0.1 decision 6's Student Override scope (flags only, not a full policy clone) against any known school requirement that might need more — e.g. does any school need a genuinely different late-fee *formula* per student (not just exempt/custom-grace/pre-approved-waiver), which the flag model can't express?
