## Admission Interface Copy

The Inquiry worklist refreshes its server result when opened or when the query changes, matching Pipeline and Applications. Returning to All Classes must refresh any cached empty result; it omits the class predicate while retaining Board, Medium, year and other active filters. No polling or extra per-render request is added.

When Inquiry handoff fails because its Inquiry form is archived, the worklist keeps a persistent shared dialog with the applicant, inquiry reference and form name. Staff with Forms View and Add can open the exact form's existing Restore confirmation; View-only staff can review the form, and staff without settings access are directed to the admission administrator. Older API responses without a form ID open Admission Forms rather than claiming to restore an unidentified form. The dialog does not restore, change the offering, or retry handoff automatically. Existing archive eligibility and offering configuration locks remain backend-owned.

The Inquiry worklist groups Board, Medium, Class, Status and Inquiry dates above the table. Choose **All Classes** or **All Statuses** to remove the corresponding restriction. Status shares the table's server filter and combines with search, dates, academic scope and other column criteria. A same-day Inquiry date selection includes that entire local calendar day. **Clear inquiry dates** removes the active interval. Status and date changes reset paging.

Inquiry row actions align with their header. **Start Application** shows progress in the affected row and prevents repeat submissions. The Follow-Up dialog uses the shared no-data illustration when history is empty and one blocking overlay across history, details and footer while loading or saving.

Handling History uses the concise action label. Assessment setup shows room capacity as a separate read-only fact, Decision History retains the existing collapsible control, and Setup student links/avatars follow Student List styling. Setup pending saves retain mounted fields and initiating button spinners alongside compact skeleton feedback.

Inquiry, Pipeline and Applications use existing content-shaped skeletons for request loading through Admission Finalization. Background refresh retains safe saved rows and details. The Inquiry and Applications tables show a thin progress indicator over the top edge during background refresh and use table-shaped skeleton rows on the first load. Opening an application keeps the list row stable and uses the workspace skeleton in the destination route. Stage and editor code-loading fallbacks follow their content shapes. Save, advance, upload and finalize actions keep their initiating button spinners where there is no blocking overlay. Global navigation and SplashScreen, document-completion progress and seat-occupancy indicators retain their existing behavior.

Admission-owned navigation, headings, breadcrumbs, fixed field labels, actions, tooltips and empty states use Title Case. This module-specific requirement overrides general sentence-case copy guidance for these surfaces. Standard plus-icon creation actions show the noun only: **Inquiry**, **Cycle**, **Form**, **Workflow** and **Offering**; their accessible names retain the creation action. **Open Applications**, **Book Session**, **Start Special Registration**, **Numbering Settings** and **Create Inquiry Link** retain meaningful wording. Preserve entered names, configured applicant questions, translations, routes, identifiers and API values exactly as supplied. Common components keep their existing contracts.

Document presets keep their original saved default names separately from display labels. Parent-message event labels likewise keep their original template identities and default subjects, so existing Communication templates remain editable without creating differently named copies.

## House Management

1. Open Student Records → House Management and select an accessible medium.
2. In Houses, click a **Visible students** count to open the house drawer. Review the current House leader and search visible house members across classes and divisions. Use **Manage house leader** in the drawer to appoint an eligible member or confirm replacing or clearing the current leader. **Delete** remains available for empty houses within the caller's scope.
3. In Assign Leaders, browse active enrolled students, including students without a house. Use a student row's division leader action to review and confirm an appointment, replacement, or removal for that student's division. The crown and guard icons identify House leaders and Division leaders respectively. A student can hold both positions and show both icons. Each icon has a tooltip on hover and focus.
4. To change membership in Assign Leaders, select a board, medium, class and division in order. Changing a parent clears its child filters. The selection column appears when a specific division is selected and the user has Add/Update access. Select students, choose **Assign or move** or **Remove from house**, and review the preview and any House leader being cleared before confirming.

View-only access retains readable workspaces without mutation controls. Busy commands lock dismissal; failed reads expose Retry, and failed writes retain the draft. Context changes discard stale selections and previews. See the [backend rules](../../../Shikshamitra-BE/docs/modules/student/product.md#house-management) for eligibility, scope and independent leadership.
